# PLAN.md — Orangery Slides

План для Claude Code. Фази по порядку, задачі по порядку. Оцінка для одного розробника + Claude Code. Кожна фаза shippable сама по собі.

Статуси: `[ ]` · `[x]` · `[~]` · `[-]` (з причиною).

Адаптера як окремого шару не знадобилось: розширення й так параметризовані опціями, тож Docs просто передає їм свої замикання (напр. `SmartTyping` читає налаштування). Тулбар лишився в Docs: він складений із кнопок Docs, спільна там лише сама кнопка. Тести реєстру розділені — механіка в пакеті, інваріанти набору команд (нема колізій шорткатів, усі id з крапкою, жодного захардкодженого Cmd) у Docs, бо це властивості його набору, а не реєстру

### 0.2 Skeleton Slides

Дві «хиби» генератора зробили фікстури кращими: `sixteen-by-nine` лишає `type="screen4x3"` при 16:9 розмірах (парсер, що вірить атрибуту замість cx/cy, на цьому падає), і кожна дека везе 11 layout-ів, з яких використано один — саме так роблять справжні деки, і жоден не можна загубити

Додався ще Caladea — метричний відповідник Cambria, серифної пари Calibri у темі Office; везти одну без другої означає лишити половину типового документа з чужими метриками. ## Фаза 1 — PPTX рідний формат (тижні 3–5)

Мета: відкрити чужу деку, побачити її правильно, зберегти без змін — PowerPoint не помічає різниці.

### 1.1 Пакет
- [x] ADR `0002-pptx-roundtrip.md`: per-shape passthrough, що моделюємо в MVP, що ні
      — головна різниця з Docs записана: у документі незмодельоване лежить *поруч* із абзацами, у деки воно *всередині* фігури. Звичайний прямокутник із текстом везе ефекти, 3D, adjustment-значення геометрії й extLst із creation id для Morph. Тому фігура не перебудовується з моделі, а патчиться на місці; незмодельований тип не перебудовується взагалі. Названо й головний ризик: забутий writer тихо не збереже правку, тож кожна змодельована властивість потребує тесту «зміни → збережи → перечитай», а не лише «розпарси»
- [~] `ooxml-presentation`: читання `presentation.xml`, `slides/*`, `slideLayouts/*`, `slideMasters/*`, `theme/*`, `notesSlides/*`, `notesMaster`, `handoutMaster`, `tableStyles`, `viewProps`, `presProps`, comments — усе в `PptxPackage`
      — пакет тримає всі частини як прочитані (це `ooxml-core`), а цей шар будує *карту*: які частини є і як вони одна на одну посилаються. Слайди, їхні layout-и й нотатки, майстри з їхніми layout-ами й темою, notesMaster, розміри. `handoutMaster` і comments поки не в карті — вони зберігаються, але ще нікому не потрібні
- [~] Порядок слайдів з `sldIdLst`, rels на layout/master/notes/media
      — порядок береться зі списку, а не з rels-файлу, і це перевірено на деці з 8 слайдів. По дорозі знайшлась Docs-специфіка, що пролізла в спільне ядро: `resolveTarget` був зашитий на `word/`, а rels слайда ходять убік через `../slideLayouts/`. Тепер резолвер приймає базову теку. Media ще не в карті
- [x] Модель: `Presentation → Master[] → Layout[] → Slide[]`, `spTree`, EMU-координати
      — слайд, layout і майстер структурно одне й те саме: частина зі `spTree`. Це не спрощення, а основа успадкування плейсхолдерів, тож змодельовано саме так. Кожна фігура тримає **той самий вузол**, з якого прочитана (перевірено тестом, що він лежить у дереві, а не є копією). Плейсхолдер без власного `a:xfrm` дає `transform: null` — це не дефект, а те, що позиція приходить з layout; записати її в слайд означало б назавжди відчепити фігуру від нього. `p:graphicFrame` має власний `p:xfrm` замість `a:xfrm` у spPr — врахував
- [~] Серіалізатор: перегенеровуються тільки змодельовані частини; `p:timing`, `p:transition` (поки), `mc:AlternateContent`, невідомі елементи — verbatim
      — механіка є й доведено обернена до парсера, але редагування ще немає, тож «тільки змодельовані частини» поки виконується тривіально. Одна знахідка вже тут: XML-декларація зберігається з оригіналу, а не пишеться наша. PowerPoint пише подвійні лапки й CRLF, python-pptx — одинарні й LF; нормалізація ламає round-trip на всіх 10 деках (перевірив пробою)
- [x] Round-trip тест: open → save без правок → структурний diff XML на всьому корпусі
      — суворіше за структурний diff: **побайтно**, на всіх 10 деках. І ще жорсткіший другий тест — кожна частина зі `spTree` примусово проганяється через парсер і серіалізатор, тож він падає, якщо вони не точно обернені, навіть на розмітці, яку ніхто не читає. Саме вона й губиться найтихіше
- [x] CI: LibreOffice headless → PDF до/після, render-diff
      — структурна рівність XML необхідна, але недостатня: два файли можуть різнитися структурно й малюватися однаково, і — випадок, що має значення — збігатися структурно й малюватися по-різному. Для деки round-trip **жорсткіший**: регенерується кожна частина з деревом фігур, бо звичайне збереження нередагованої деки байт у байт те саме, і малювати його двічі нічого не доводить. Харнес винесено у `packages/render-diff`, і другий споживач одразу показав, що в ньому було зайвого: шлях до корпусу, розширення й те, що означає round-trip, — це все, чого він не знав про формати

### 1.2 DrawingML → модель
- [~] `sp`: `spPr` (xfrm, prstGeom 180+ пресетів — таблиця path-ів, custGeom), fill (solid/gradient/pattern/picture/none), line (width, dash, caps, arrows), effects (shadow базово; решта passthrough)
      — читається все п'ять видів заливки, лінія з товщиною, пунктиром, торцями й стрілками, пресетна геометрія з `a:avLst`. `p:style` тепер резолвиться через `a:fmtScheme`: більшість фігур у реальній деці не вказують заливки взагалі, а несуть «третя заливка теми, кольором accent1», і тема пише свої заливки через `phClr`, який підставляє саме посилання. Без цього фігури з шаблону малювались би порожніми. Індекс одиничний, а нуль означає «без заливки», а не «перша» — переплутати означає зробити непрозорими всі навмисно прозорі фігури. Наскрізне правило: **відсутнє ≠ none**. Фігура без `a:solidFill` бере заливку зі style reference або плейсхолдера, а `a:noFill` — свідомо прозора; злиття цих двох зробило б кожну нестилізовану фігуру або невидимою, або не того кольору. Тому `null` усюди означає «не вказано». Значення `a:avLst` зберігаються — це радіус кута й розмір вістря, тобто рівно те, що губиться при перебудові фігури з моделі «це заокруглений прямокутник». Таблиця path-ів для 180 пресетів — робота рендерера (1.3); `custGeom` позначається, але шлях не моделюється; ефекти лише детектуються
- [~] `txBody`: `bodyPr` (insets, anchor, wrap, autofit, columns), `lstStyle`, `a:p`/`a:r`/`a:pPr`/`a:rPr` → ProseMirror через `editor-text`
      — OOXML-бік готовий, і міст у ProseMirror теж: тіло читається в документ і записується назад. Редагування тексту це єдине місце, де фігуру не можна патчити поелементно — набір розбиває рани, зливає й видаляє їх, тож абзаци перебудовуються. Але **те, що ран несе**, не перебудовується: кожен зберігає свій `a:rPr`, і запис патчить його, а не замінює. Ран, у якого змінили накреслення, повертається зі своєю мовою, підсвіткою й extLst і однією іншою літерою; ран, якого не чіпали, повертається побайтно. Перевірив пробою: writer, що будує `a:rPr` заново, валить два тести. Тіло, тіло-властивості й `lstStyle` не чіпаються взагалі. Далі — власне редактор у полотні. Три речі, які легко втратити й які мають тести: `a:endParaRPr` (єдине, що несе порожній абзац — без нього гине форматування кожного порожнього рядка деки), ран із самого пробілу (це текст між двома словами, а не порожній ран), і `fontScale` в `a:normAutofit` (PowerPoint читає власне значення назад; перерахунок без нього змінив би розмір тексту в кожній деці при відкритті). Міст у ProseMirror ще попереду
- [x] Bullets: `buChar`, `buAutoNum`, `buBlip`, `buNone`, рівні 0–8 з lstStyle успадкуванням
      — усі чотири види читаються, разом із шрифтом, що несе гліф. `buNone` відрізняється від «нічого не сказано»: перше це рішення файлу, друге — успадкувати з рівня. Успадкування: ланцюг з шести рівнів, властивості зливаються по полях. Ключове — **`p:txStyles` майстра лежить не там, де решта**: не на фігурах-плейсхолдерах, а поруч із деревом фігур, і їх три (title/body/other) за типом плейсхолдера. Без цього кроку падають п'ять тестів, і показово як: заголовок тихо отримує шрифт тіла `+mn-lt` замість `+mj-lt` — не збій, просто неправильний шрифт скрізь
- [x] `pic`: blip, crop (`srcRect`), transforms
      — обрізання читається як частка з кожного боку, кожна сторона окрема й необов'язкова; `stretch` і `tile` розрізняються
- [x] `grpSp`: вкладені трансформи (chOff/chExt), `cxnSp`: конектори з прив'язкою до фігур
      — група називає **два** прямокутники: де вона стоїть і в яких координатах написані її діти. Координати дитини самі по собі не означають нічого. У фікстурі дитина каже `x=914400`, а сидить на `4572000` і на 20% ширша за вказане — читач, який бере `a:off` дитини як позицію на слайді, малює групи не там і не того розміру, і тим гірше, чим далі групу посунули. Довелось додати справжню групу в корпус: python-pptx їх не робив, і математику не було на чому перевірити
- [~] `graphicFrame`: таблиці (`a:tbl`) повністю; діаграми, SmartArt, OLE — як bounding box + passthrough (діаграми — рендер у 1.4)
      — таблиця читається з сіткою, висотами рядків, властивостями клітинок і межами. Головне: **об'єднання не видаляє клітинок**. Верхня ліва несе `gridSpan`/`rowSpan`, а кожна поглинута лишається у файлі з прапорцем `hMerge`/`vMerge`. Їх не можна ні малювати, ні викидати — сітка перестане сходитись, і PowerPoint відмовиться відкривати файл. Вид графіки визначається за `uri` на `a:graphicData`, а не за вмістом: діаграма й SmartArt обидві містять один елемент із самим лише relationship id, і більше нічим не відрізняються. Рендер діаграм — 1.4
- [x] Placeholder-резолвер: `p:ph` type/idx → layout → master, злиття властивостей; тести на кожен рівень
      — два кроки зіставляються **по-різному**, і це головна пастка схеми. Слайд→layout іде за `idx` (layout може мати кілька body). Layout→master іде **за типом**, бо індекси між ними не пов'язані: у типовому майстрі PowerPoint дата це `idx="2"`, а в layout — `idx="10"`. Зіставлення за `idx` не знайшло б нічого, а відкат «бери першу» віддав би даті геометрію заголовка — перевірив пробою, тести падають саме так. Майстер має лише п'ять видів, тож усе, що тримає контент (obj, subTitle, pic, tbl, chart, dgm, media), успадковується від body — це не спрощення, іншого там просто немає. Успадковане резолвиться при читанні й ніколи не пишеться назад
- [x] Theme: `clrScheme`, `fontScheme` (major/minor, latin/ea/cs), `fmtScheme`; `schemeClr` з `lumMod/lumOff/tint/shade/alpha`
      — палітра, дві гарнітури і `a:fmtScheme` читаються, колір лишається **символічним** і резолвиться лише при малюванні. Головне тут — `p:clrMap` на майстрі: фігури й тема говорять різними словниками (`tx1` проти `dk1`), і без мапи `schemeClr val="tx1"` не резолвиться взагалі. Модифікатори зберігаються в порядку запису, бо вони не комутативні; `lumMod`/`lumOff`/`satMod`/`satOff` рахуються в HSL, `tint`/`shade` — по каналах. Робота з темою переїхала з Docs у спільний пакет: `a:theme` однаковий у документа й деки. `ea`/`cs` гарнітури ще не читаються

### 1.3 Рендер (read-only)
- [~] SVG-рендерер слайда: фон (solid/gradient/picture, з master), фігури, текст (через ProseMirror у режимі read-only або статичний HTML), картинки, таблиці, групи
      — фігури, текст, групи, фон, картинки й таблиці малюються. Координати лишаються в EMU аж до viewBox: перетворення в пікселі десь по дорозі зробило б кожну позицію округленням. Текст живе в `foreignObject` **усередині** SVG, а не шаром поверх: `<text>` у SVG не переносить рядки, а viewBox тоді масштабує текст разом із фігурами без жодних вимірювань у JS. Перша спроба була шаром поверх зі `scale(calc(100% / …))` — CSS так не вміє, масштаб має бути безрозмірним. Пресети: таблиця з ~25 найуживаніших, решта малюється габаритним прямокутником — це видно на екрані й нічого не коштує файлу. Фон майже завжди приходить з майстра — слайд і layout мовчать, тож рендерер, який читає лише слайд, фарбує все біле випадково, а не навмисно. Обрізання картинки робиться кліпом: у SVG немає crop, тож зображення малюється більшим і обрізається назад. У таблиці об'єднаний блок малює та клітинка, що ним володіє, а поглинуті пропускаються — але рахуються при обчисленні колонки, інакше сітка роз'їдеться. Лишились autofit і ефекти
- [~] Autofit: вимірювання тексту після рендеру, `fontScale`/`lnSpcReduction` як у PowerPoint (±1 pt допуск)
      — записаний масштаб **застосовується**: PowerPoint стискає текст, що не вміщається, і записує, до чого стиснув. Ігнорувати це означає малювати текст повного розміру, тобто виводити його за межі фігури рівно так, як PowerPoint вирішив не виводити. Обчислення *нового* масштабу після правки потребує вимірювання тексту після верстки — це вже редагування, не читання
- [~] Filmstrip з thumbnail-ами (offscreen render → bitmap, кеш)
      — мініатюра це той самий рендерер меншого розміру, а не окремий шлях малювання: одна дорога до слайда означає, що мініатюра не може розійтися з полотном. Рендер у bitmap і кеш — задача продуктивності з фази 4, на десяти слайдах ще не окупається
- [x] Notes панель показує `notesSlide`
      — нотатки лежать у плейсхолдері типу `body` на сторінці нотаток; другий плейсхолдер там це картинка самого слайда, показувати її вдруге нема сенсу
- [x] Банер warnings для непідтримуваного, як у Docs
      — збирається обходом деки, а не записується під час парсингу: парсер не має думки про те, що вміє намалювати рендерер, і при такому розділенні додавання пресета прибирає попередження без жодної правки в OOXML-шарі. Повідомлення групуються по слайдах, а від п'яти слайдів рахуються, а не перелічуються — банер із сорока номерами ніхто не читає. Про те, що малюється правильно, банер мовчить: попередження про справний рендер привчає ігнорувати банер

### 1.4 Діаграми read-only
- [~] `c:chart` парсер: bar/col, line, pie/doughnut, scatter, area; серії, категорії, підписи, легенда, осі
      — читається з **кешу**, а не з формул: кожна серія вказує на діапазон у вбудованій книзі Excel, а поруч лежить кеш того, що там було. PowerPoint теж малює з нього, тому діаграма рендериться й у файлі, з якого книгу вирізали. Точки розріджені — у них є `idx`, а `c:ptCount` каже справжню довжину; читач, який складає значення в порядку документа, тихо зсуває все після пропуску. Scatter читається як серія значень, але окремого рендера ще не має; підписи даних не читаються
- [x] SVG-рендер із кольорами теми; решта типів — bounding box "Chart"
      — стовпчикові, лінійні, площинні, кругові й кільцеві. Решта отримує рамку з написом, а не наближення: радарна діаграма, намальована стовпчиками, була б брехнею, а порожня рамка чесно каже, що на слайді щось є. Кольори серій беруться з акцентів теми, як у PowerPoint. Діаграма малюється у власній системі координат і масштабується в рамку — геометрія в EMU зробила б підпис осі тисячною пікселя
- [x] На save — passthrough, `c:*` не чіпаємо
      — частина діаграми зберігається цілою; рендер лише читає, тож шляху, яким звідси могла б з'явитися `c:*` розмітка, просто немає

**DoD:** 20 дек корпусу — 0 регресій round-trip; візуально ≥ 95 % збіг із PowerPoint на скріншотах.

## Фаза 2 — Редактор (тижні 6–9)

### 2.1 Виділення і трансформації
- [x] Клік/Shift-клік/marquee, вибір у групі (подвійний клік входить у групу)
      — клік і Shift-клік були раніше. Ціль кліку — прозорий прямокутник над фігурою, тож фігура без заливки все одно клікабельна (так поводиться й PowerPoint). Виділення належить слайду: перехід на інший його скидає, бо ті самі id там означають інші фігури. Тепер решта, і головне з'ясувалось дорогою: **групи не виділялись узагалі** — клік по члену групи виділяв саме його, тобто протилежне до всього, що вміє групувати. Тепер група це одна річ, доки в неї не зайшов: клік по члену виділяє групу, подвійний клік заходить на **один** рівень (стрибок одразу на дно зробив би вкладеність невидимою, а вихід — несподіванкою), `Escape` виходить назад по одному й лишає щойно покинуту групу виділеною. Оскільки групу не малюють, рамку довелось рахувати окремо від того, що намальоване, а перетягування мусить нести все, що в ній: «виділене» для перетягування — це збіг за id **або за будь-яким предком**. Член групи, який тягнуть зсередини, пишеться в координатах групи, а перетягування виміряне на слайді, — тож дельта переводиться через `intoGroupSpace`, інакше фігура у зменшеній групі їхала б не туди, і тим сильніше, чим більше групу стискали. Marquee ловить **повністю охоплене**, як PowerPoint: із «дотиком» смуга через середину щільного слайда забирає все, і жесту, який вибирає кілька, не лишається. Ловить те, що на поточному рівні — верх слайда або нутро відкритої групи, — тобто рівно те саме, що виділяє клік. Побічно знайдено справжній дефект диспетчера клавіш: вимкнена команда робила `return` із усього циклу, а не `continue`, тож перша ж вимкнена команда з'їдала клавішу в решти. З одним обробником на клавішу це було невидиме; Escape на двох командах це оголив
- [x] Move/resize (8 ручок)/rotate, Shift/Alt-модифікатори, стрілки nudge
      — перетягування, вісім ручок (поки чотири кутові), Shift обмежує вісь і тримає пропорції, Alt тягне від центра; nudge стрілками через реєстр. Масштаб пікселів у EMU береться з прямокутника SVG **на початку кожного перетягування**: захоплений при монтуванні, він став би неправильним після першої зміни розміру вікна. Слухачі висять на вікні, а не на фігурі — курсор, що зійшов із фігури посеред перетягування, це норма. Дельта коміситься один раз при відпусканні, тож перетягування через слайд це один крок скасування, а не сто. Спершу зроблено **запис**, а не ручки: за ADR 0002 головний ризик у тому, що змодельована властивість без writer-а тихо не зберігається, і це падає непомітно, на відміну від втрати розмітки. Трансформа тепер патчиться в самому піддереві фігури: після правки позиції в ній лишаються її геометрія, заливка, посилання на стиль і текст, а **всі інші частини пакета побайтно ті самі**. `rot="0"` і `flipH="0"` не пишуться, а видаляються — інакше кожен збережений файл відрізнявся б від відкритого без жодної правки людини. Плейсхолдер, який не мав власної трансформи, отримує її першою дитиною `p:spPr`, бо інакше PowerPoint пропонує «відремонтувати» файл. Тепер ручок вісім, а не чотири, і є поворот. Ручка ребра рухає **одне** ребро: потягнути верх убік не має робити нічого, і саме в цьому вся різниця між ребром і кутом — тому Shift тримає пропорції лише на кутах, бо на ребрі це рухало б те, чого ніхто не хапав. Поворот міряється від центра фігури до вказівника **до і після**, і різниця додається до наявного кута: брати абсолютний кут вказівника означало б, що фігура стрибком доганяє курсор тієї ж миті, коли ти за неї взявся. Shift прилипає до 15°, як у PowerPoint, кут тримається в межах одного оберту. Заради цього перетягування довелось навчити не лише зсуву, а й позицій: у різниці немає центра, від якого міряти. Рамка повертається разом із фігурою, тож ручки лишаються на її кутах, а не на кутах коробки, яку фігура займала б неповернутою
- [x] Smart guides: центр слайда, краї, інші фігури, рівні відстані; лінійки й направляючі (drag з лінійки)
      — допуск перераховується з пікселів, а не задається в EMU: «достатньо близько» це відстань на екрані, і слайд, зменшений учетверо, інакше прилипав би вчетверо здалеку. Рівні проміжки рахуються лише між фігурами, які перекриваються по іншій осі: два боксики в ряд стоять рівномірно, а боксик і щось у кутку — ні, і назвати це збігом означало б прилипати до випадковостей. Вирівнювання сильніше за проміжок. Корекція рахується **один раз від прямокутника навколо всього виділення** — перетягуючи три боксики, рухаєш одну річ — і та сама корекція йде і в те, що намальовано, і в те, що записано: фігура, яка прилипла на екрані й не прилипла у файлі, це найгірше з обох. Напрямні живуть у `viewProps.xml`, як і в PowerPoint: ніщо на слайді з ними не вирівняне після закриття файлу. `p:guide/@pos` — у восьмих пункту, єдина одиниця у всьому форматі, яка не EMU і не відсоток
- [x] Z-order: вперед/назад/на передній/на задній план
      — атрибута z немає: порядок малювання це порядок у `p:spTree`, тож «вперед» означає посунути елемент пізніше серед сусідів. Кілька фігур рухаються **блоком**: піднімати їх по одній означало б переставити їх одна повз одну. Перевірка «вже на місці» спершу дивилась на позиції й була неправильна для незв'язного виділення — тепер результат будується й порівнюється з наявним, що і коротше, і правильне саме в тих випадках, де арифметика помилялась. Нічого не рухається перед `p:nvGrpSpPr`/`p:grpSpPr`, які не є фігурами
- [x] Align/distribute (до слайда або до виділення), flip H/V
      — одна фігура вирівнюється до слайда, кілька — до власних меж виділення: вирівняти одну саму до себе означало б не зробити нічого. Розподіл зрівнює **проміжки, а не центри**: фігури різного розміру з рівно розставленими центрами виглядають нерівно, і саме заради цього команда й існує. Крайні дві не рухаються — вони задають проміжок, який ділиться, тож потрібні три фігури. Flip тепер є, і дорогою знайшлось більше, ніж сама команда: модель читала й писала `flipH`/`flipV`, але **ніщо їх не малювало**. Тобто будь-яка чужа дека з віддзеркаленою стрілкою показувалась неправильно, і не тільки — картинки взагалі не оберталися й не дзеркалились. Тепер і фігури, і картинки розміщуються однаково: дзеркало пишеться **після** повороту, щоб застосуватись **до** нього, бо SVG читає список трансформ справа наліво, а OOXML дзеркалить геометрію й аж потім повертає результат; інший порядок ставить відзеркалену й повернуту стрілку не з того боку коробки. Дзеркалиться лише геометрія — слова у фігурі лишаються як написані, бо дзеркальне речення це не те, що хтось мав на увазі під «відобразити», і не те, що показує PowerPoint. Кожна фігура дзеркалиться навколо **власної** середини, а не виділення навколо своїх меж: інакше рухались би фігури, яких ніхто не просив рухати
- [x] Group/ungroup зі збереженням трансформів
      — при створенні групи `chOff`/`chExt` ставляться **рівними** її `off`/`ext`, тобто відображення тотожне й **ніщо не рухається**. Будь-який інший вибір масштабує кожну дитину в мить групування: перевірив пробою — з `chOff="0"` фігури стрибають на пів дюйма, і падають три тести. При розгрупуванні позиція кожної дитини резолвиться через групу й **записується**, бо після зникнення групи її власні координати нема проти чого читати. Група стає на місце найпереднішого учасника, тож порядок малювання не змінюється. Перевірено повним колом: згрупувати → зберегти → перечитати → розгрупувати → зберегти → перечитати, і все стоїть точно там, де стояло
- [x] Copy/paste/duplicate (`Mod+D`) фігур між слайдами й деками; paste зберігає позицію або зміщує
      — дублювання в межах слайда: копіюється **вузол**, тож із ним іде все, чого модель не читає — ефекти, extLst, будь-яка розмітка. Змінюється лише id, бо дві фігури з одним id у частині це файл, який PowerPoint відкидає. Зсув іде тим самим writer-ом, що й будь-яке інше переміщення, а не другою реалізацією, яка могла б із ним розійтися. Копії стають виділенням — наступне, що з ними роблять, це рухають. Тепер є й буфер: через **системний**, а не змінну у вікні, бо «між деками» означає між двома вікнами, а кожне вікно — окремий webview з окремим усім. Переноситься текст, бо буфер носить текст; що це JSON із XML усередині — нікого більше не стосується, а чуже лишається браузеру. Переїздить **ціле піддерево**, тож із фігурою їдуть її ефекти й усе, чого модель не читає. Те, чого не можна перенести як XML, — це те, на що XML показує: `r:embed` картинки називає зв'язок у слайді, з якого копіювали, а той слайд може бути у файлі, про який друге вікно ніколи не чуло. Тому байти їдуть разом, а зв'язок робиться заново на місці; зв'язок, який перенести нема як, **видаляється**, а не лишається висіти — id, що не називає нічого, це файл, який PowerPoint пропонує «відремонтувати». Вставка на той самий слайд зміщує на чверть дюйма (дві фігури в одному місці виглядають як одна, і людина подумає, що нічого не сталося), на інший — лишає позицію. Cut видаляє **лише після** того, як копія лягла: різати й видаляти, коли копіювання не вдалося, — єдиний спосіб, яким ця команда може втратити роботу. Запасна копія в пам'яті вікна є тільки на випадок, коли буфер **не читається взагалі**: якщо він прочитався й там чужий текст, це означає, що людина скопіювала щось інше, і відповідати своєю пам'яттю на її намір не можна — цю ваду зловив тест
- [x] Undo/redo транзакційний, 100+ кроків
      — одиниця скасування це **частина пакета**, а не модель: правка змінює розібраний XML на місці (саме це зберігає незмодельоване), тож незмінної моделі, чиї старі версії можна тримати, тут просто немає. Частина слайда важить кілька кілобайт, і сотня таких дешевша за будь-яку хитрішу механіку. Після скасування модель перечитується з пакета — інакше вона показувала б фігуру на новому місці, поки файл каже інше. Межа 200 кроків

### 2.2 Фігури
- [x] Панель вставки: пресети (прямокутник, еліпс, стрілки, callouts, зірки, блок-схема) — малювання drag-ом
      — галерея пропонує **тільки ті пресети, які цей застосунок справді малює**: запропонувати інший означало б покласти на слайд прямокутник під чужим ім'ям, а людина дізналася б про це на чужому екрані. Тест ходить по списку й звіряє кожен запис із таблицею геометрії, тож розсинхрон неможливий. Заради «callouts» і «блок-схеми», яких не існувало, додано шість геометрій — рішення, термінатор, дані, підготовка і дві виноски; виноска це коробка з хвостом, і хвіст — це все, що робить її виноскою. Мініатюри малюються **тією самою** функцією, що й слайд, тож обране це те, що з'явиться. Вибір не кладе фігуру, а **озброює** її: наступний drag на слайді каже де і якого розміру. Це та сама смуга, що й рамка виділення, з однією різницею — що робиться з областю; смуга на порожньому слайді означає «ось ця ділянка» в обох випадках. Після однієї фігури інструмент роззброюється, як у PowerPoint: намалювати п'ять прямокутників це п'ять рішень, а інструмент, що лишився б озброєним, перетворив би кожен наступний клік по слайду на шостий. Натиск, який починає малювання, не скидає виділення — це натиск, щоб малювати, а не щоб зняти виділення
      — сім пресетів через меню, фігура з'являється по центру слайда. Головне: нова фігура **не пише власних кольорів**, а несе `p:style` на першу заливку й лінію теми в accent1 — інакше вона ігнорувала б тему деки й виділялася б поруч із усім, що там уже є. Малювання drag-ом попереду
- [~] Лінії та конектори з прив'язкою до точок фігур; редагування точок
      — з'єднання двох виділених фігур із **прив'язкою**, а не просто лінією поруч: без `a:stCxn`/`a:endCxn` лінія виглядає з'єднаною рівно доти, доки щось не посунули. Сторони обираються за віссю, на якій фігури далі одна від одної — вибір найближчої пари точок провів би лінію **всередині** двох фігур, що перекриваються. Конектор, який іде назад, отримує `flipH`, а не від'ємний розмір. Дві фігури рівно: при трьох команда сіра, бо трійка не каже, яку пару з'єднати. Перетягування кінців і редагування точок попереду
- [~] Fill/line/shadow редактори в properties панелі, кольори теми + custom, gradient editor
      — заливка й лінія для виділення, зміна кількох фігур це один крок скасування. Правило «відсутнє ≠ none» тримається й на записі: очищення заливки пише `a:noFill`, а не видаляє елемент — видалення повернуло б фігуру до її style reference, тобто до іншої фігури, ніж просили. Кольори теми, градієнти й тіні попереду
- [x] Текст у будь-якій фігурі; `bodyPr` — anchor, insets, wrap, autofit (Shrink on overflow / Resize shape / None)
      — `a:bodyPr` це коробка, а не слова: де текст стоїть у ній, скільки місця лишається по краях, чи переноситься довгий рядок і що поступається, коли тексту більше, ніж місця. «From layout» **прибирає атрибут**, а не пише сьогоднішню відповідь: фігура без `anchor` бере його з плейсхолдера, і ці двоє однакові рівно доти, доки не зміниться layout. Прохання «стискати» пише порожній `a:normAutofit` — PowerPoint сам записує, до чого вже стиснув, і зчитує власне число, тож здогадка тут змінювала б розмір тексту при відкритті. Фігура, намальована деінде, може не мати `p:txBody` зовсім; він створюється при вході в неї — і це в сторі, а не в полотні, бо входів декілька, а той, який не підключили, це той, що втрачає набране
- [~] Картинки: вставка з файлу/буфера/drag, crop (двоклік → crop mode), заміна, прозорість, скидання
      — вставка з файлу. Разом мають змінитись чотири речі, і дека без будь-якої з них змушує PowerPoint пропонувати ремонт: байти, content type, relationship **із цього слайда** (у деки в кожного слайда свій rels-файл, на відміну від документа з одним) і сам `p:pic`. Пакетну частину винесено в `ooxml-core` — Docs робив те саме з `word/media`, і другий споживач показав, що це спільне; ціль relationship тепер пишеться відносно власної теки rels-файлу, тож у слайда виходить `../media/…`, а в документа — `media/…`. Буфер, drag, crop і заміна попереду
- [~] Таблиці: вставка N×M, рядки/стовпці, об'єднання, стилі з `tableStyles`
      — вставка 3×3 з рівним поділом. Таблиця не фігура: це `a:tbl` усередині `p:graphicFrame`, тож рамка носить свій `p:xfrm`, а сітка живе всередині. **Кожна клітинка створюється одразу**, порожня — розрідженої форми не існує, і таблиця з відсутнім `a:tc` це файл, який PowerPoint відкидає (та сама причина, чому об'єднання зберігає поглинуті клітинки). Стиль береться з `def` у `tableStyles.xml` самої деки, а не із зашитого GUID: інакше кожна дека отримувала б однакову таблицю незалежно від своєї теми. Додавання рядків, об'єднання й вибір розміру попереду
- [x] Іконки (bundled SVG-набір) — вставляються як `sp` з `custGeom`, щоб пережити PowerPoint
      — картинка не бере кольори теми, розмивається на великому слайді й не дає PowerPoint нічого, з чим працювати. Той самий контур як `a:custGeom` — звичайна фігура: заливається з теми, обводиться, масштабується, і кожен інструмент, який уже знає, що робити з фігурою, знає, що робити з нею. Набір **побудований із чисел**, а не скопійований рядками шляхів: набір, написаний руками, це набір, де ніхто не скаже, що зірка п'ятикутна, поки не подивиться. Дуги не наближаються, а відхиляються: `A` це сегмент еліпса з власною параметризацією, і перетворення її на безьє — рішення про припустиму похибку, яке нема кому тут ухвалювати. Полотно тепер малює `custGeom` власним контуром; фігура з дугою відступає до прямокутника, у якому стоїть, бо три чверті фігури гірші за коробку

### 2.3 Текст
- [x] Редагування тексту в фігурі через `editor-text`: B/I/U/S, шрифт, розмір, колір, підсвітка, superscript, caps, spacing
      — усе це властивості run-а в обох форматах, тож живуть на тій самій мітці `textStyle`, що й розмір із гарнітурою, і в спільному пакеті, а не в застосунку. Кольори мітка носить **лише як hex**: `accent1` не має де жити в мітці, зробленій за формою CSS, тож тематичний колір лишається там, де його написали, і мітка його ніколи не чіпає — run, пофарбований темою, далі за нею йде. Звідси асиметрія: `null` у мітці стирає колір лише там, де він від початку був буквальним. Атрибути, які міст моделює, пишуться **авторитетно**: `null` — це редактор, який каже «тут цього немає», і відновити його зі збережених властивостей означало б правку, якої тихо не сталося
- [~] Абзаци: вирівнювання, рівні (Tab/Shift+Tab), інтервали, відступи, bullets (символ, нумерація, картинка), колонки
      — вирівнювання, буліти (символ, нумерація, без буліта), міжрядковий інтервал і рівні через Tab/Shift+Tab, дев'ять, з зупинкою на краях. Повторний вибір того самого вирівнювання **знімає** його, а не лишає: так успадковане повертається, замість того щоб сьогоднішню відповідь заморозити у файлі. Те саме з булітом — «вимкнути» означає «успадкувати з рівня», а не «жодного»; це різні речі, і `a:buNone` пишеться лише коли його справді просили. Тест спіймав тонке: прогін **без правок** додавав `a:buFont` поруч із наявним `a:buChar`, тож буліт тепер пишеться лише коли він відрізняється від того, що у файлі. Колонки й відступи попереду. Схема редактора отримала атрибути OOXML-абзаца: без них ProseMirror **мовчки викидає** рівень і вирівнювання на першому ж натисканні, бо схема просто ігнорує невідомі атрибути. І тут же спрацював ризик із ADR 0002 у чистому вигляді: рівень читався, редагувався й **не зберігався** — `pPr` писався дослівно. Тест «зміни → збережи → перечитай» це спіймав, writer тепер патчить `lvl` і `algn` на наявний `pPr`, лишаючи решту (буліт, відступи) недоторканою
- [x] Placeholder-текст ("Click to add title") зникає при наборі, порожній placeholder не пишеться в файл
      — підказка малюється й **ніколи не пишеться**: дека з незайманих плейсхолдерів має відкриватись деінде порожніми блоками, а не словом «Title». Текстовий блок, який хтось спорожнив навмисно, мовчить — у нього нема чого підказувати. Дата, колонтитул і номер слайда теж мовчать: їх заповнює показ, а не набір, тож підказка була б неправдою
- [~] Find & Replace по всій деці
      — пошук і заміна по всіх слайдах і клітинках таблиць. Збіг **не зважає на межі ранів**: «Presentation» може бути записана трьома ранами, бо хтось виділив жирним середину, і пошук по одному рану її б не знайшов, хоч людина бачить одне слово. Тому рани абзаца склеюються, збіг шукається в цілому, а заміна пишеться назад через ті рани, які він накрив: **весь текст іде в перший з них**, решта втрачає свою частину — так робить PowerPoint, а розподіл нового тексту по старих ранах за довжиною фарбував би літери за тим, де випадково стояли попередні. Заміна по деці — **один крок скасування**, для чого історія тепер тримає кілька частин на крок. Покрокового переходу між збігами ще немає
- [x] Автозаміна як у Docs (лапки, тире), spell-check — `[-]` до появи в Docs
      — те саме розширення `editor-text`, тож правила однакові в обох аппах. Мова береться з тексту біля курсора, а не з інтерфейсу: дека українською на англійській збірці все одно хоче «», а не "". Вставка приходить простим текстом — CSS із браузера не має потрапляти на слайд, бо саме оформлення деки й робить її декою

### 2.4 Слайди
- [x] Новий слайд (з layout поточного), дублювати, видалити, drag-reorder у filmstrip, multi-select
      — новий слайд, видалення й переміщення вгору/вниз. Слайд це **частина пакета**, а не вузол документа, тож узгодити треба п'ять речей: саму частину, її rels, content type з її іменем, relationship із `presentation.xml` і запис у `p:sldIdLst`. Порядок показу задає **лише список**, тому переміщення не торкається жодної частини — і тест перевіряє, що `slide1.xml` після переміщення просто стоїть у списку іншим за чергою. Новий слайд бере плейсхолдери свого layout порожніми, але **без дати, колонтитула й номера**: їх малює layout, а копія на слайді була б другою, яка перестала за ним іти. Видалити останній слайд не можна — презентацію без слайдів PowerPoint не відкриє. Дублювання копіює частину **як текст**, а не перезбирає з моделі: усе, чого ми не змоделювали, їде разом із нею. Rels копіюються теж, тож копія дивиться на той самий layout і ті самі картинки — медіа спільне, інакше дека з копій росла б на мегабайт щоразу. Виняток — сторінка нотаток: спільна означала б, що нотатки, набрані на копії, переписують оригінальні. Filmstrip має **власний вибір**, окремий від показуваного слайда, бо це різні питання: один слайд на екрані, а дій над слайдами може стосуватися будь-яка їх кількість
- [x] Зміна layout зі збереженням контенту placeholder-ів (mapping за type/idx як у PowerPoint)
      — змінюється **лише relationship**. Плейсхолдер називає, що він таке, і резолвиться проти того layout, на який дивиться слайд, тож текст лишається й бере нову геометрію та стилі; частина слайда після цього байт у байт та сама, і тест саме це стверджує. Список layout-ів — ті, що пропонує master слайда, у порядку самого master
- [x] Секції (`p14:sectionLst`) — назви, згортання у filmstrip
      — секцій немає у вихідній схемі: PowerPoint 2010 додав їх розширенням на `p:presentation` під uri, якого більше ніхто не вживає. Секції **розбивають список слайдів на послідовні відрізки** — нічого іншого файл виразити не може, — тож модель тримає лише те, **де секція починається**, а решта випливає. Саме тому слайд, перетягнутий через межу, опиняється в іншій секції, і нікому не треба про це казати. Списки у файлі щоразу **перезбираються з меж**, а не патчаться: це єдиний спосіб, за якого слайд не може опинитися у двох секціях. Кожна операція зі списком слайдів після себе вирівнює секції, бо дека, де ці двоє не згодні, показує у PowerPoint слайди поза всіма секціями. Згорнутість — стан вікна, а не документа
- [x] Фон слайда: колір/градієнт/картинка, "приховати графіку master"
      — відсутній і «немає» тут різні речі, і різниця більша, ніж для фігури: слайд без `p:bg` бере фон layout, той — master. Тож «From layout» **видаляє елемент**, а «None» пише `a:noFill` і зупиняє успадкування. `a:effectLst` пишеться навіть порожнім — без нього PowerPoint пропонує полагодити файл. Заразом з'явився запис градієнтів (`a:gradFill`), яким користується й панель фігури. Полотно тепер малює **меблі layout і master** — усе, що не плейсхолдер: плейсхолдери це шаблони, і малювати їх означало б показувати на кожному слайді «Click to add title». `showMasterSp` вимикає це на кожному щаблі окремо
- [x] Заголовки слайдів у outline-режимі (панель Outline: заголовки+текст placeholder-ів, редагування там же)
      — показує **лише плейсхолдери**: фігура, яку намалювали, щось означає тим, що вона в цьому місці слайда, а плейсхолдер — це слайд, який каже «оце заголовок», і саме з цього складається outline. Вільні текстові рамки не вгадуються. Редагується тим самим мостом ProseMirror, що й полотно, тож набраний тут заголовок зберігає форматування своїх run-ів. Власний прапорець редагування, не `editing` зі стору деки: інакше полотно відкрило б другий редактор на тому самому тексті, і обидва писали б у файл
- [x] Notes: редагування, зберігається в `notesSlide` з правильним master
      — редагуються тим самим мостом ProseMirror, що й текст на слайді: нотатки несуть форматування, як будь-який текст, і зведення їх до рядка втратило б його при першому ж відкритті панелі. Пишуться у **власну частину**, слайд лишається недоторканим — на це є тест. Слайд без сторінки нотаток чесно про це каже: створення такої сторінки — окрема операція, а вдавати інше означало б втратити набране
- [x] Slide size: 16:9 / 4:3 / custom, масштабування контенту при зміні
      — кожна координата на слайді це EMU проти прямокутника `p:sldSz`, а не його частка, тож зміна розміру лишає вміст там, де він був — на вужчому слайді це означає «за краєм». Тому пропонуються ті самі два варіанти, що й у PowerPoint: лишити як є або вписати. Вписування масштабує **меншим із двох відношень** і центрує результат: масштабувати осі окремо означало б зробити з кожного кола еліпс. Масштабуються й layout-и з master-ами — слайд, що змасштабувався б без свого layout, відірвався б від нього. Групам чіпають лише власний xfrm: група задає прямокутник, у який відображаються її діти, тож вони масштабуються разом із нею один раз
- [x] Zoom canvas 25–400 %, fit, `Mod+0`
      — за замовчуванням вписано у вікно, бо слайд має фіксовану форму й корисно майже завжди бачити його цілком. Перший крок від «вписано» — натуральний розмір, а не здогадка про те, що показувало вікно

### 2.5 Master і теми
- [x] Перегляд master/layouts (Slide Master view): редагування placeholder-ів, фонів, шрифтів теми
      — layout і master структурно те саме, що й слайд: частина з деревом фігур. Тож це **не другий редактор**, а те саме полотно, наведене на іншу частину — усі інструменти фігур і текст працюють без змін. `editDeck` тепер охоплює всі частини з деревом фігур, а не лише слайди: зміна, що дійшла до layout і не була записана, була б зміною, якої файл не побачив. Команди про слайди там вимкнені — вони нічого не кажуть про layout
- [x] Галерея тем: "Orangery" (чорний/оранжевий, Inter) + 6 нейтральних; застосування теми до деки перефарбовує через `schemeClr`
      — жодна фігура не чіпається. Фігура, яка каже `schemeClr accent1`, уже каже «те, що тема зве акцентом 1», тож зміна теми змінює, чим її намальовано — у цьому весь сенс непрямості, і тому застосування теми це маленька правка однієї частини, а не прохід по всій деці. Фігури з буквальним кольором його лишають, і це чесний наслідок того, що їх пофарбували кольором, а не слотом. Тема застосовується до **всіх master-ів**: дека, де master-и не згодні про accent1, це дека, де один слот означає два кольори
- [x] Шрифти теми (major/minor) у дропдауні як "Heading / Body"
      — пишуться як `+mj-lt` і `+mn-lt`, а не як родина, у яку вони резолвляться сьогодні: різниця між «цей заголовок — шрифт заголовків» і «цей заголовок — Inter» у тому, що перше йде за декою при зміні теми. Заразом виявилося, що у Slides не був підключений `FontFamily`, тож атрибут, який міст вичитує з `a:latin`, не мав де жити — обрана в панелі гарнітура просто зникала б
- [ ] Збереження власної теми як `.thmx` — `[-]` до запиту

**DoD:** зробити 15-слайдову деку з нуля без миші там, де це можливо; відкрити її у PowerPoint — все на місці, включно з placeholder-ами й темою.

## Фаза 3 — Показ і вивід (тижні 10–11)

### 3.1 Слайд-шоу
- [x] Окреме вікно на весь екран на вибраному дисплеї (Tauri multi-window), `F5` з початку, `Shift+F5` з поточного
      — `F5` з початку, `Shift+F5` з поточного, і редактор лишається там, де був: «показувати звідси» означає звідси, а не «і залиш мене там». Показ і presenter — **окремі вікна**: webview не може бути у двох місцях, а presenter, намальований поверх редактора, це presenter, якого бачить зала. Дека потрапляє туди **файлом**: вона й так лягає на диск при кожному збереженні, а слати пакет через IPC як JSON-масив чисел — це мегабайти тексту про те, що вже є байтами. Вікно читає деку саме, тож перезавантажене посеред показу повертається на те саме місце. Усе, що може не вийти — немає Tauri, немає другого екрана, дека не записалася, — відступає до показу в поточному вікні: презентація, яка не почалася, гірша за презентацію не на тому екрані
- [x] Навігація: клік/space/стрілки/PgUp/PgDn/Home/End, `N`+Enter, `B`/`W`, `Esc`
      — клавіші обробляються в самому показі, а не через реєстр команд: показ це режим із власною клавіатурою, і `b` у реєстрі це bold. Число набирається по цифрі й береться на Enter; число, яке не називає слайда, **не робить нічого** — тихо перегорнути слайд було б найгіршою відповіддю на помилку набору. `B`/`W` лишають місце під собою, і будь-який рух повертає екран: погашений показ, який непомітно перегорнувся, лишає доповідача розповідати про інший слайд
- [x] Presenter view на іншому дисплеї: поточний, наступний, нотатки (масштабований шрифт), таймер, годинник, сітка слайдів для стрибка
      — п'ять речей, які насправді потрібні тому, хто стоїть перед залою, і нічого, що змагається за той самий погляд. Малює ті самі слайди тим самим рендерером: presenter, який міг би розійтися з екраном, гірший за жоден — сенс саме в тому, щоб знати, на що дивиться зала, не обертаючись. З одним екраном presenter не відкривається взагалі: він був би тим, що бачить зала
- [x] Транзиції: none/fade/push/wipe з тривалістю з файлу; решта → fade, `p:transition` зберігається
      — формат називає близько сорока, ми вміємо малювати чотири. Решта це **не «без переходу»**: між слайдами щось мало статися, і шахівниця, якої ніхто не просив, ближча до fade, ніж до різкої зміни. Тому все, чого не вміємо, стає fade, файл лишає написане собі, і дека, повернута в PowerPoint, далі розчиняється. Тривалість — єдине число не з вихідної схеми: PowerPoint 2010 додав `p14:dur` у мілісекундах, зазвичай усередині `mc:AlternateContent`, а `spd` це три слова, тож мілісекунди перемагають. Перехід беруть **зі слайда, до якого йдуть**, як у PowerPoint: дека, де слайд 4 з'являється плавно, робить це з будь-якого слайда, звідки ти на нього прийшов
- [x] Анімації: не грають, об'єкти у фінальному стані; `p:timing` verbatim
      — `p:timing` це найбільше в деці, чого тут ніхто не моделює, і найімовірніший кандидат на тихе зникнення в серіалізаторі, який перезбирає зрозуміле. Тож перевірка **жорстка**: кожна частина проганяється через parse і serialise, і жоден елемент timing не має пропасти. Другу половину «об'єкти у фінальному стані» довелося дописати: фігура з `hidden="1"` не малювалася ніде, а ми її малювали. Це не про анімацію — прихована фігура прихована до показу й після нього, — але виявилося саме тут. Слайд гортається цілком: кроків збірки, які можна було б прокликати, немає, і редактор каже про це банером, а не лишає з'ясовувати на сцені
- [x] Відео/аудіо: playback з media parts, автоплей за `p:timing` — базово; клік запускає
      — відео на слайді це **картинка першого кадру** з relationship на фільм поруч; картинка — те, що малює кожна програма, поки хтось не натисне play, і єдине у файлі, що має розмір і місце. Програвач з'являється лише під час показу: у редакторі це був би контрол, який змагається з виділенням і рухом того, на чому він сидить. Коли починати — читається з `p:timing` рівно настільки: у фільму там свій вузол, і `delay="indefinite"` означає «коли попросять», тобто клік, а затримка в мілісекундах — «разом зі слайдом». Читати більше й не треба: решта timing описує анімації, які тут не грають. Клік по програвачу не гортає слайд — у показі клік будь-де гортає, а клік по відео означає «грай відео». Тип частини береться з `[Content_Types].xml`, а не з розширення: звук, записаний у файл `.vid`, — саме той випадок, де здогадка хибна
- [x] Гіперпосилання на слайд/URL клікабельні в показі
      — формат пише **три різні речі тим самим елементом**: посилання на веб це relationship із зовнішнім target, посилання на слайд це relationship на його частину, а «наступний слайд» не має target узагалі й каже про це в `action`, бо в пакеті нема чого називати «наступним слайдом». `ppaction://media` вживає той самий елемент і посиланням **не є** — це те, як відео каже, що воно відео, — тож розв'язується в ніщо, а не в стрибок, якого ніхто не просив. Клікабельно лише під час показу: у редакторі клік по фігурі виділяє її, і посилання, яке забрало б цей клік, зробило б кнопку неможливою до пересування. Адреса відкривається **назовні**: презентація, яка пішла з себе, це презентація, що скінчилася
- [~] Тест на проекторі/другому моніторі на macOS: перемикання дисплеїв, sleep не вбиває вікно
      — це не код: потрібні дві фізичні панелі, проєктор, який домовляється про режим, і машина, яка засинає з вікном на дисплеї, що потім зникає. Нічого з цього не існує в тестовому середовищі, і саме воно й ламається на сцені. Чек-ліст написано — `apps/slides/docs/presenting-checklist.md`; прогнати його має людина

### 3.2 Експорт
- [x] PDF: слайди, з нотатками, handouts 2/3/6 на сторінку; шрифти вбудовані
      — PDF виходить із **власного друкарського конвеєра браузера**, а не з нашого PDF-писаря. Другий спосіб малювати слайд це другий спосіб малювати його неправильно, а цей уже вміє найважче — текст, що переноситься, шрифти, які треба вбудувати, розмір сторінки, який не A4, — бо це той самий рендерер під `@media print`. Заразом «експорт у PDF» і «друк» стають одним механізмом, а не двома, які не згодні між собою, — чим вони й є в операційній системі. Слайди друкуються **розміром слайда**: дека 16:9 на A4 це та сама картинка з двома білими смугами, а PDF деки має бути декою. Усе, де на сторінці більше одного слайда, — це папір, і папір це A4
- [~] PNG/JPEG кожен слайд або поточний; SVG поточного
      — слайд малюється у вузол, який не потрапляє у вікно, **тим самим рендерером**, і з нього забирається SVG. Малювати його по-іншому заради експорту було б другим способом намалювати неправильно, а брати з вікна означало б експортувати те, що там опинилося, — включно з рамкою виділення. Картинки всередині вже data URL, тож файл стоїть сам; шрифти **названі, а не вбудовані** — це єдине в експортованому SVG, що не те, що ти бачив. PNG/JPEG — це те саме через растеризатор браузера, і чи впорається він із HTML усередині `foreignObject`, це питання до рушія, а не до цього коду: WebKit був у цьому непослідовним роками. Тому провал **кажеться вголос**, а не пишеться на диск порожньою картинкою — і саме растр треба перевірити руками (`apps/slides/docs/presenting-checklist.md`)
- [x] ODP імпорт/експорт (свій шар, passthrough-підхід)
      — **конвертація, а не другий рідний формат**, і це відхилення від того, як зроблено ODT у Docs, тож варте пояснення. Docs тримає ODT як ODT, бо документ — це текст у будь-якому разі. Дека — це пакет майстрів, layout-ів і плейсхолдерів, чиє успадкування розв'язує кожен рендерер, команда й редактор у застосунку; друга модель за всім цим — це не формат, це другий застосунок. Тому читач видає опис, плаский настільки, щоб із нього збудувати справжній `.pptx`: сторінки, рамки і те, що в них, у позиції, яку дав файл. Рамки кладуться **абсолютно**, а не на наші плейсхолдери: імпорт має показувати те, що каже файл, а не те, що волів би наш майстер. Рівні списку туди й назад: у PresentationML рівень — це число, в OpenDocument — вкладеність у `text:list`, і конвертер єдиний, хто мусить знати обидві мови. Відкрита ODP **не має шляху**: записати нашу конвертацію поверх чужого `.odp` означало б замінити документ, який ми зрозуміли лише частково, на такий, який лише частково написали, і першого ж разу, коли це мало б значення, воно з'їло б деку. Тому збереження питає куди й пропонує `.pptx`, а банер каже, що саме не переїхало. Експорт — окрема команда поруч зі SVG/PNG, а не «зберегти як»: він не змінює того, чим є відкритий документ. Те, чого не вдалося записати (геометрія, таблиці, діаграми), **рахується**, а не зникає мовчки. `mimetype` пишеться першим і без стиснення — саме це дозволяє читачеві впізнати файл за першими байтами, не розпаковуючи; заради цього в `ooxml-core` з'явився параметр `stored`, бо стиснення запису — властивість zip-контейнера, а не котрогось із форматів. Фікстури будуються в тестах, а не лежать бінарниками: ODP — це zip з XML, і тест, який показує XML, що читає, каже, що саме він перевіряє. Чого він показати не може — що з ним згодна Impress, — лишається за корпусом і людськими очима
- [x] Друк через системний діалог
      — той самий механізм: `Mod+P` кладе деку на сторінку й відкриває системний діалог, у якому й живе «зберегти як PDF»

### 3.3 Файли
- [x] New/Open/Save/Save As/Close, recent, `.pptx`/`.odp` "Open with", drag-and-drop, кілька вікон
      — New: дека **вже `.pptx`** до того, як потрапляє в редактор — збудована, зазипована й відкрита тим самим шляхом, яким іде файл із диска. Тримати нову деку в якомусь легшому вигляді означало б, що перше збереження — це конвертація, а конвертація це там, де щось губиться. Майстер і шість layout-ів (Title Slide, Title and Content, Section Header, Two Content, Title Only, Blank) виписані руками, а не згенеровані з коротшого опису: layout — річ фіксована, і опис, який породив би шість штук, був би другою мовою, яку треба вчити, з тією ж геометрією плейсхолдерів усередині. Перший слайд додається через `addSlide`, а не пишеться поруч із layout-ами, — інакше він був би єдиним слайдом у застосунку, який ніхто не створює так, як усі решта. Тема береться з галереї, а не описується вдруге. Побічний наслідок: нова дека не має шляху, тож autosave довелось навчити нести весь пакет — без цього New був би єдиним місцем, де крах з'їдає роботу. Close тепер **питає**, і не тільки він: New, Open, Close і саме вікно всі прибирають деку з екрана, тож усі чотири йдуть через один шлюз — одне питання, одне формулювання, три відповіді, замість чотирьох місць, кожне з яких мусило б пам'ятати спитати. Закриття вікна ветує Rust і віддає питання фронтенду, бо «чи є незбережене» знає дека, а дека живе там. Чиста дека проходить без жодного слова: підтвердження, яке з'являється щоразу, — це те, яке навчаються клацати не читаючи, і тоді воно не спрацьовує саме там, де було потрібне. «Не зберігати» стирає й снапшот: лишити його означало б запропонувати цю ж роботу при наступному запуску як ніколи не втрачену, тобто рівно протилежне щойно сказаному. А «Зберегти», яке наткнулося на скасований Save As, **не йде далі**: дека лишається такою ж незбереженою, якою була, і закрити її тоді означало б викинути саме те, що людина просила лишити. Save і Save As зроблено поза чергою: `file.save` був заглушкою, тобто **все, збудоване у фазах 2–3, жило лише в пам'яті**. На диск іде **пакет**, а не модель: усе, чого ми не зрозуміли, досі в ньому. Запис через Rust — тимчасовий файл поруч і перейменування на місце, чого webview не вміє, — і копія того, що було, лишається з тієї ж причини. Дека, якої ніколи не зберігали, не має куди йти, тож Save питає те саме, що й Save As, а не тихо не робить нічого. Undo після збереження знову позначає файл зміненим: дека, збережена й відкочена, справді відрізняється від файлу. Recent, «Open with» і drag-and-drop прийшли разом, бо це те саме: спосіб отримати деку без діалогу вибору файлу. Усі три йдуть через той самий шлюз незбереженого, що й Open, — кинути файл не на те вікно це помилка руки, і вона не має коштувати години роботи. Сам список переїхав у `packages/platform` (це вміст теки app data, а нею володіє саме цей пакет), випадання — в `ui-kit`, а вичитування шляху запуску — в `tauri-shared`: усі три були в Docs, і другу копію писати не було потреби. Список тримається в сторі, а не перечитується з диска, коли щось схоже на зміну: пише його відкриття деки, і компонент, що стежив би за декою, читав би рівно на мить раніше — щоразу показуючи список без того файлу, який щойно відкрили. Файл, який не відкрився, у список не потрапляє. Кілька вікон майже нічого не коштували — кожне вікно це окремий webview, отже окремий стор, — але оголили те, що з одним вікном було невидиме: **`Emitter::emit` у Tauri широкомовний**, на чому б його не викликали. Тобто `window:close-requested` питав би всі вікна, і чуже відповідало б за себе, закриваючись; а `document:open-path` із `open_window` повертався б у вікно, яке щойно віддало файл, і воно відкривало б ще одне вікно, і ще, поки хтось дивиться. Обидві події тепер адресні — **за міткою**, а не за `WebviewWindow`: остання збігається лише зі слухачем, який рантайм класифікував так само, а як саме зареєструвався JS-слухач, вирішувати не нам. Це був живий дефект і в Docs, тож виправлення спільне. Кинутий файл на змінену деку тепер не питає нічого: він іде в **нове вікно**. Питання доречне, коли людина сама просила замінити деку; промах мишею — не прохання, і відповідь на промах у тому, щоб він нічого не коштував. ODP лишається поза цим пунктом
- [x] Atomic write, `.bak`, autosave, відновлення після краху — з `tauri-shared`
      — запис і `.bak` уже були: обидва йдуть через ту саму Rust-команду, що й у Docs, бо перейменувати файл webview не вміє, а недописана дека — це дека, якої ніхто не поверне. Бракувало снапшотів. Снапшот **не є декою**: це різниця між тим, що у вікні, і файлом, з якого вона відкрита, а на відновленні файл перечитується і різниця накладається зверху. Писати цілий `.pptx` кожні п'ять секунд було б простіше й чесніше на вигляд, але ціль — 300 слайдів із картинками, і перезиповування десятків мегабайтів на кожну паузу в роботі людина відчуває саме тоді, коли механізм, що береже її роботу, працює. Тому стор веде список частин, які розійшлися з диском, і рахує його **не за історією скасувань**: вставлена картинка додає медіа-частину й переписує файл зв'язків, жодна з яких не є кроком, який хтось відміняє, і обидві потрібні — без них відновлений слайд показує на картинку, якої немає. Видалення слайда окремо не записується, бо його нема: `removeSlides` прибирає запис із `sldIdLst` і лишає частину сиротою, тож змінений `presentation.xml` описує видалення повністю. Таймер перезапускається на кожній зміні, а не цокає за розкладом, — снапшот пишеться, коли людина зупинилась, а не посеред перетягування фігури. Дека, яку ніколи не зберігали, не має від чого рахувати різницю, тож її снапшот несе **весь пакет**: це дорога форма, і вона доречна саме там, де застосовується, — у нової деки на диску немає нічого, на що можна відкотитись, і вона ж найменша
- [x] Медіа > 20 МБ: пропозиція стиснути картинки при збереженні (як PowerPoint)
      — **пропозиція, ніколи не дія**. Зменшення картинки — єдина правка в застосунку, якої не скасувати, перевідкривши файл, тож вона ніколи не є наслідком чогось іншого, про що просили. Питання виникає лише для деки, достатньо важкої, щоб її було незручно надсилати, **і** лише коли є що вигравати: 20-мегабайтна дека, чиї картинки й так завбільшки як намальовані, ні про що не питається. Формат не змінюється: PNG лишається PNG, JPEG — JPEG. Конвертація між ними означає інший content type, іншу назву частини і зв'язок, який треба переписати, а для PNG із прозорістю — білий прямокутник там, де була прозорість; самого масштабу вистачає майже на все, що несе фотографія, кинута на слайд. Ціль — 150 ppi від того розміру, яким картинку намальовано, і **найбільшого** з розмірів: один файл може стояти на трьох слайдах, і підгін під найменший розмив би два інші. Пропорції беруться від самої картинки, а не від рамки: широке фото у квадратній рамці обрізає заливка, і переписати файл під форму рамки означало б це обрізання вкарбувати. Рішення відокремлене від виконання — воно все арифметика над заголовками файлів і трансформами, тож перевіряється в тесті, де canvas немає; сам ресайз приймається параметром. Заради заголовків з'явився `imageSize` у `ooxml-drawingml`: розмір читається з перших байтів, а не декодуванням сорокамегапіксельного фото заради двох чисел (він же закриє давню діру — вставлена картинка досі лягає квадратом, бо її ніхто не міряв). Картинка, яка після перекодування **побільшала**, кладеться назад: скріншот пласких кольорів легко росте, а «стиснення», що збільшило файл, було б брехнею рівно там, де тобі довірили роботу. Скасування не пише на диск нічого
- [x] Шаблони при створенні: порожня, з темою, 5 стартових дек (pitch, лекція, звіт, захист диплому, портфоліо)
      — шаблон це **тільки вміст**. Під ним той самий пакет, той самий майстер, ті самі шість layout-ів і тема з галереї, тож вибір шаблону не змінює, чим є файл, — лише те, що на ньому написано. Це і робить їх дешевими в додаванні й неможливими для структурної помилки. Кожен слайд додається через `addSlide` — той самий виклик, що й команда «додати слайд», — отже шаблон не може створити слайд, якого сам застосунок створити б не зміг. Текст кладеться новим `setShapeText`, який приймає прості рядки з рівнями списку: те, що набирають, іде через ProseMirror, бо він для набору, а все інше, що породжує текст — шаблон, вставлений план, згенерована дека, — має рядки й рівні й нічого більше, і змушувати його спершу будувати документ редактора означало б вчити його мови, яка йому не потрібна. Заповнення йде **другим проходом** по деці, як вона зрештою стоїть: додавання слайда перечитує пакет, і фігури, які тримали до того, — це фігури розбору, на який уже ніхто не дивиться. Самі п'ять — це форма аргументу, а не оздоба: що має відповісти pitch, через що проходить лекція, про що питають на захисті. Хто зітре всі слова, лишиться з кістяком деки. Вибір пропонується списком того, для чого кожен, а не мініатюрами: шаблони різняться будовою аргументу, а не виглядом, і картинка з шести слайдів однієї теми не сказала б нічого. Питання про незбережене ставиться **після** вибору шаблону: спитати до нього, а потім почути «нічого, передумав», — це питання ні про що

**DoD:** лекція на 40 слайдів із відео проведена з presenter view на проекторі без збоїв.

Мета: окремі завантаження лишаються за замовчуванням; з'являється один інсталятор "Orangery" з вибором, що ставити.

### Спільне
- [ ] ADR `000N-suite-distribution.md`: окремі бінарники, окремі bundle id, окремі теги (`docs-vX`, `slides-vX`), спільна версія suite (`suite-vX`) як snapshot сумісних версій
- [ ] Updater: один endpoint, канали по апп; suite-оновлення = оновлення кожного встановленого аппа окремо
- [ ] Асоціації файлів не перетинаються: `.docx/.odt/.rtf` → Docs, `.pptx/.odp` → Slides; жоден інсталятор не реєструє чуже
- [ ] Спільна тека налаштувань `<appdata>/Orangery/{docs,slides}`, спільні bundled fonts (один раз на диску)
- [ ] Лендинг: три кнопки на апп + "Завантажити все"

### Windows
- [ ] Один NSIS `.exe` з components page: Docs ☑, Slides ☑ (пізніше Sheets); Tauri NSIS-шаблон розширити
- [ ] Спільні файли (шрифти, runtime) ставляться раз; uninstall кожного аппа окремо
- [ ] winget: окремі манифести на апп

### macOS
- [ ] Один DMG з обома `.app` і ярликом Applications — людина тягне що хоче; без `.pkg` з галочками
- [ ] Окремі DMG лишаються основним шляхом
- [ ] Homebrew casks: `orangery-docs`, `orangery-slides`

### Linux
- [ ] Окремі `.deb`/AppImage на апп + мета-пакет `orangery-suite` (Depends на всі)
- [ ] Спільний пакет `orangery-fonts` для bundled шрифтів
- [ ] Flathub — за запитом

**DoD:** на Windows один інсталятор ставить вибрані аппи, на macOS обидва варіанти працюють, на Linux `apt install orangery-suite` тягне все.

## Ризики

| Ризик | Мітигація |
|---|---|
| Витягування пакетів із Docs зламає Docs | Фаза 0.1 має DoD "1446 тестів + корпус зелені"; ніяких змін логіки, тільки переміщення |

| Анімації люди чекають одразу | Чесно в лендингу: "зберігаються, не грають (поки)"; passthrough гарантує, що нічого не втратиться |
